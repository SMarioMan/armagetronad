# Armagetron Advanced in the browser (WebAssembly + WebGL)

The `webgl` branch runs Armagetron Advanced 0.2.9.3.0 as a WebAssembly module
in the browser: SDL1 through emscripten's JS port, the game's fixed-function
OpenGL pipeline through emscripten's legacy GL emulation, and every data file
preloaded into the virtual filesystem.

Live site: <https://smarioman.github.io/armagetronad/>. Every push to this
branch rebuilds the game and republishes that site automatically
(`.github/workflows/webgl-pages.yml`).

## Branch lineage

`webgl` branches from the `v0.2.9.3.0` tag (`036daaf3`), which sits on
`trunk`'s history: the port builds on that release, with SDL1 through
emscripten's SDL1 port, the release's own autotools build, and its UDP netcode.

`trunk` has moved on to 0.4 development - SDL2 + protobuf, 666 files under
`src/` changed against 0.2.9.3.0 - so this branch deliberately does not carry
those commits: the port is not a patch set for that tree, and mixing the two
leaves a source tree that neither the 0.2.9 nor the 0.4 build system can
configure.  Giving 0.4 a web build means re-applying the same design there -
the WebSocket transport in `nSocket.cpp`, the event-loop frame driver, the three
generated-JS patches, building the `resource/` maps before the link - as new
work.

## Layout

| path | purpose |
|---|---|
| `webgl/build.sh` | configure + make + post-build JS patches, then assembles `webgl/dist/` |
| `webgl/setup_toolchain.sh` | installs the pinned emsdk and cross-builds libxml2 for wasm |
| `webgl/SDK_VERSION` | the emsdk version this port is pinned to |
| `webgl/emscripten.cache` | autoconf cache for the wasm cross-configure, generated by `build.sh` |
| `webgl/patch_*.py` | post-build fixes applied to the generated JS (see below) |
| `webgl/site/index.html` | the player page; copied into `webgl/dist/` |
| `webgl/site/lodtest.html` | floor sampler level-of-detail page; measures its own output (see _Comparison instrumentation_) |
| `webgl/serve.py` | local static server for `webgl/dist/` |
| `webgl/proxy/proxy.js` | WebSocket↔UDP bridge so the client can reach real servers |
| `webgl/dist/` | build output (gitignored) — this is what gets deployed |

## Building

Prerequisites: `git`, `curl`, `python3`, `make`, `g++`, `autoconf` ≥ 2.69,
`automake` ≥ 1.16, `pkg-config`. Network access is needed for the toolchain
download.

```sh
./webgl/setup_toolchain.sh   # emsdk (webgl/SDK_VERSION) + libxml2 for wasm
./bootstrap.sh               # regenerate configure / Makefile.in
./webgl/build.sh             # wasm build  -> webgl/dist/
./webgl/serve.py             # serve on http://127.0.0.1:8080
```

Environment knobs: `EMSDK_DIR`, `LIBXML2_PREFIX`, `SDK_VERSION`,
`DOWNLOAD_DIR`, `JOBS`, `CLEAN=0|1`, `PORT`.

`bootstrap.sh` needs pkg-config's `pkg.m4` macro (`/usr/share/aclocal/pkg.m4`).
Without it `aclocal` succeeds quietly but emits an `aclocal.m4` with no
`PKG_CHECK_MODULES` definition, so `configure` is generated carrying three
unexpanded calls and aborts part way through with
`syntax error near unexpected token 'XML2,'`.  An autoconf built outside the
system prefix does not search the system aclocal directory, so it needs
`ACLOCAL_PATH=/usr/share/aclocal ./bootstrap.sh`.

There is no emscripten port of libxml2, and the resource manager needs it to
parse the XML resources, so `setup_toolchain.sh` cross-compiles libxml2 2.9.14
as a static library. `webgl/build.sh` runs configure with
`--host=wasm32-unknown-emscripten`, a cross-compile cache
(`webgl/emscripten.cache`) and `-D` overrides that point every install path at
the preload root; the native build is untouched.

## What was changed in the game

Wasm-specific code sits in new files or inside `#ifdef __EMSCRIPTEN__` blocks,
so native builds compile and behave exactly as before.

| area | change |
|---|---|
| `src/tools/tWasmLoop.{h,cpp}` | The blocking frame loops (`while (OnFrame()) {}`) are driven from the JS event loop via `emscripten_set_main_loop`. Nested loops, exit actions and continuations are supported; `main()` hands over to the event loop at the first loop and never returns, so the startup chain (language menu → first setup → main menu) is re-entered as steps (see `src/tron/gArmagetron.cpp`). Asyncify was deliberately not used: re-entering `main()` re-runs initialization and desyncs input. |
| `src/network/nSocket.cpp` | The browser has no UDP sockets, so Armagetron datagrams ride WebSockets. Proxy mode opens **one multiplexed session** (`<Module.ARM_PROXY_BASE>?mux=1`): each message carries a 9 byte header naming the peer it concerns, the destination outbound and the sender inbound, so the discovery broadcast costs one socket instead of one per port and its answers stay attributable. A bridge that does not speak mux is recognised by its missing `AGMUX1` banner (or 1.5 s of silence), and the client falls back to the per-destination shape `?target=<ip>:<port>`, replaying what it had buffered; `?mux=0` asks for that shape directly. Direct mode `ws(s)://<ip>:<port>` remains one socket per connection: the server's own listener has no framing. One WebSocket message is exactly one Armagetron datagram; datagrams sent while a session is still opening are queued and flushed on open. |
| `src/render/rScreen.cpp` | Display init for a canvas that follows the window: `sr_WasmWindowResized(w,h)` (exported) re-inits the display for the "desktop" screen mode; GL context/attribute handling for WebGL. |
| `src/render/rEmscriptenGLU.h` | GLU is not available in the emscripten GL stack: `gluPerspective`, `gluLookAt`, quadric/mipmap helpers reimplemented on plain GL. |
| `src/render/rSysdep.cpp`, `rGL.*`, `rDisplayList.cpp`, `rViewport.cpp` | Single-buffered WebGL swap (skip the color-buffer clear that would wipe the frame), `GL_QUAD_STRIP` handling, display-list limits, texture unit state. |
| `src/render/rTexture.cpp` | Image loading reads the file from the virtual FS (`fread` + `IMG_Load_RW`); the alpha convention matches native SDL_image, so no `IMG_InvertAlpha`. |
| `src/render/rModel.{cpp,h}` | emscripten's legacy GL emulation can only hand WebGL 16-bit indices: its client-array `glDrawElements` path copies `count << 1` bytes out of the caller's array and calls `GLctx.drawElements` with a hard-coded `GLctx.UNSIGNED_SHORT`. The coherent-model branch passed the 32-bit face array, so the port read it as halves and every triangle `(A,B,C)` became `(A,0,B)` then `(0,C,0)`: light cycles mangled up close, collapsed to slivers far away. The face list is re-emitted as `GLushort` on that branch only, held as a member because the display list records the pointer the draw call was given and replays it on later frames. |
| `src/engine/eSound.cpp` | The SDL1 JS port has no `SDL_LoadWAV`, so a small RIFF/WAV parser loads effects; the mix callback buffer is explicitly zeroed (the JS port reuses one buffer, which otherwise accumulates samples forever). No music mixer. |
| `src/engine/eTimer.cpp`, `src/tools/tSysTime.*` | Frame timing and the clock driven from the animation-frame cadence. |
| `src/tools/tDirectories.cpp`, `tResourceManager.cpp`, `tConfiguration.cpp` | No binreloc in the browser: paths resolve to the preload root, user data to `$HOME/.armagetronad/var` (mounted as IndexedDB by the page). |
| `src/ui/uMenu.*`, `uInput*.cpp` | Menu rendering/keyboard handling for the event-loop model and browser focus rules. |
| `src/tron/*` | Startup sequence, splash/logo handling, server browser/favorites for the transport change. |
| `src/tron/gCycle.cpp` | Two cycle primitives the fixed-function emulation draws wrong are routed around on the port only: the chat pyramid's triangle pair goes through client arrays (the emulation counts that primitive's vertices from one uniform stride, gets 5.2 for six and drops the last), and the headlight fan is compiled out (its radial falloff needs a `GL_ARB_fragment_program`, which the emulation cannot express). Both are `#ifdef __EMSCRIPTEN__`; see "Cycle geometry the emulation mis-sizes" below. |
| `src/render/rSDL.h`, `src/render/rSDL12KeySyms.h`, `src/ui/uInputQueue.*` | The port's SDL layer numbers non-ASCII keys `0x400 \| SDL2 scancode` while the game, its configuration defaults and its `.aarec` archives are all SDL 1.2 numbering.  A generated header redefines the 56 SDLK_* constants whose numbers differ and `su_GetSDLInput()` runs incoming browser events (numbers in `0x400..0x4FF`) through the same pair table, while numbers that already came out of an archive pass through untouched, so bindings, replayed input and HUD key labels match the desktop. |
| `src/tron/gMenus.cpp`, `src/render/rScreen.cpp` | Display settings that cannot act in a browser are not offered in the port's menus, and the values behind them are pinned at display init: truecolor textures (WebGL has no paletted or colour-index upload), smooth shading (`glShadeModel` is a stub in the fixed-function emulation, which interpolates vertex colours unconditionally), dither (WebGL has no dither state; the emulation records the `GL_DITHER` cap in its enable table and never reads it), keep-window-active (`sr_Activate()` forces the app active on this platform, so the branch the switch selects is never taken), display lists (`rDisplayList.cpp` compiles no list under `__EMSCRIPTEN__`), vsync (its only two consumers, the `SDL_GL_SetAttribute(SDL_GL_SWAP_CONTROL, ...)` calls in `sr_InitDisplay`, are excluded for this platform and the browser paces swaps itself), colour-depth and Z-buffer-depth (they reach `SDL_GL_SetAttribute`, but the page has created the WebGL context before the game asks for one and a canvas keeps the attributes of the context created first), fullscreen and both size selections (`lowlevel_sr_InitDisplay` rewrites the chosen size to "desktop", which tracks the live window, and the page owns the real fullscreen state through its button and the canvas double-click), and the texture filters: trilinear mip-mapped for floor, wall and object, bilinear for fonts, the combination the far-grid measurements settled on. Each item is a `#ifndef __EMSCRIPTEN__` guard around its menu entry, so the desktop build's menus are byte-for-byte what they were. |
| `src/tools/wdbg.h` | Console logging that compiles to nothing unless the build adds `-DWASM_DBG`. |

## Post-build JavaScript patches

emscripten generates JS that the game cannot use as-is; `webgl/build.sh` runs
these patches on `src/armagetronad_main.js` after every link:

- `patch_sdl_convert.py` — `SDL_ConvertSurface` calls `drawImage(null)` on
  surfaces whose 2D canvas `IMG_Load_RW` discarded in `SDL.GL` mode; falls back
  to a heap-buffer copy. Without it the game froze on the first game start.
- `patch_gl_emulation.py` — the legacy GL emulation lacks immediate-mode
  `GL_QUAD_STRIP`, used for player walls; the mode is retargeted to
  `GL_TRIANGLE_STRIP`, which the wall's vertex order already is.
- `patch_line_eyeclip.py` — this renderer *drops* a line segment whose two ends
  have opposite clip-space w rather than clipping it, and the game folds its
  camera into the projection, so any segment running back past the eye simply
  disappears. Measured in a bare WebGL1 page with the very matrices of replay
  frame 363: a straddling segment paints 0 of 4017 probed pixels with no GL
  error, while a triangle under the same matrix clips correctly at 4004/4017.
  `src/render/rRender.h` (`atglDrawArrays`) already cuts those segments for the
  draws routed through client arrays; this patch covers the rest, because the
  game calls `glBegin`/`glVertex2f`/`glVertex3f`/`glEnd` directly in
  `engine/eDisplay.cpp`, `tron/gSparks.cpp`, `tron/gExplosion.cpp`,
  `tron/gWinZone.cpp`, `engine/ePath.cpp`, `render/rFont.cpp`, `ui/uMenu.cpp`
  and the debug-line helpers. The cut runs in `GLImmediate` at `glEnd`, where
  the vertex block is finished and interleaved, and line-family primitives come
  out as clipped `GL_LINES` pairs, so a strip with a piece removed cannot
  connect across the gap. Triangles are left exactly as they were; they clip
  correctly here. Arm `window.arma_lineclip_debug` to print the vertex layout
  the patch found plus a keep/drop/split tally per draw.
  A draw with nothing actually cut is left completely alone: re-emitting an
  untouched polyline as separate pairs costs extra blended pixels at every
  join, which measured worse against the reference. Measured on the
  frame-exact `n363` pair of the perimeter replay (desktop pose 107.8338
  69.5185, camera height 16.4540; port 107.8338 69.5183, 16.4542):
  green-dominant pixels below row 520 go from 258 to 3008 against the
  desktop's 5307, saturated green over the lower half of the frame from 2936
  to 10283 against the desktop's 10684. Both states come from a single build
  with nothing but the page URL differing: `&nolineclip=1` switches the cut
  off, so a live page can measure the pair itself. Whole-frame agreement with
  the desktop sits in the 3.5 to 3.9 mean-channel-difference band either way
  -- each build re-simulates the ten AI players locally, so run-to-run world
  differences move that figure more than this cut does.
- `patch_emulation_fixes.py` — the fixed-function fragment shader is hardcoded
  to `precision mediump float`, which bands fog, trail fades, floor lighting
  and per-vertex wall alpha on desktop WebGL; promoted to `highp`.
- `patch_texture_projective_coords.py` — the emulation samples textures with
  `(textureMatrix * texCoord).xy` and discards the coordinate's fourth
  component, but the infinite floor and sky planes in `src/engine/eDisplay.cpp`
  encode their perspective falloff in exactly that component (`glTexCoord4f`
  with `w=1` at the near vertex, `w=0` along the rim), so the falloff those
  planes encode in that component was being dropped.  Whether that alone
  changes the picture is a separate question from conforming to the spec; the
  shader text the running page emits is the way to check any of these took
  effect.
- `patch_light_colormaterial.py` — the generated lighting pass took every term
  from the `glMaterialfv` state, and lighting the material the game actually sets
  is brighter than the desktop build: on the frame-identical `n814` pair at
  gt 10.06 the wall strip read mean bright luminance 162 against the desktop's
  88, and in the frame-exact `myrec2` pair (port `n726`, desktop `n731`, pose
  69.6229 against 69.6130, heading identical) the 120x110 box over the two
  opponent cycles read max luminance 202 with 183 px above 120 against the
  desktop's max 107 with none. The patch feeds the vertex colour into ambient,
  diffuse, emission and the material alpha instead. **This is not the GL
  colour-material rule**: `GL_COLOR_MATERIAL` is disabled by default, nothing in
  `src` calls `glColorMaterial` or enables that token, and the desktop light-state
  probe confirms the material terms do not track the vertex colour (with the
  current colour at (1,1,1), material ambient still reads the GL default 0.2).
  The emulation does implement `glMaterialfv` -- the generated glue initializes
  `materialDiffuse` to 0.8 and uploads it -- so it is not missing material state
  either; it is a stand-in for a lighting-state difference that is still open. The
  frame-exact A/B says what it buys and what it costs: in that box the patched
  port keeps the desktop's ceiling (max 107, zero px above 120, the desktop the
  same) but lights 1402 px where the desktop lights 2021, while the unpatched
  port lights 1985 px -- 98 % of the desktop's area -- with the blowout above.
  Whole-frame agreement is a tie (full mean 14.24 desktop, 14.29 patched, 14.30
  unpatched). Emission is the term with the strongest evidence: on the frame-exact
  `n363` pair the desktop has 3865 saturated green pixels in the near band below
  row 520 and a port tracking only ambient and diffuse has none there.

  The substitution is now conditional, and the reason it has to be is measured.
  The emulator feeds `a_color` from a *generic* attribute value when the draw has
  no colour array bound, and the cycle body is drawn exactly that way: the
  page-side per-draw snapshot shows `drawElements TRIANGLES n123/n243` with
  `a_normal=on`, `a_color=off` and a generic `a_color` of `(1,0,1,1)`.
  Unconditional substitution therefore threw the body's green channel away and
  took its alpha from whatever `glColor` an earlier immediate pass had left
  behind; an alpha left at 0 by a fading trail hides the body outright.  The patch
  now uploads `getVertexAttrib(colorLocation, VERTEX_ATTRIB_ARRAY_ENABLED)` once
  per lit draw and the shader picks vertex colour or material uniforms on that
  flag.  The pname matters: the version first shipped asked for
  `ATTRIB_ARRAY_ENABLED`, which is not a WebGL constant, so the query was
  rejected with INVALID_ENUM and answered null -- 3285 rejected calls in a run
  frozen at recSec 16.033 of the reference replay, 6111 at 20.023 -- which pinned
  the flag at 0 for every lit draw and filled the console until Chrome stopped
  reporting WebGL errors at all.  Counting the corrected query on the same frozen
  replay: one `u_colorFromArray` location, 3285 uploads, all of them 0, because
  every lit draw in this recording is a model draw with the colour array off --
  exactly the case the condition was written for -- so the two captures are
  byte-identical 382141-byte PNGs and nothing shipped changes visually.  What the
  fix restores is the condition's input and the error stream.
  Pose-matched `perp2` pair, both builds at `n352`, gt 2.6519, camera 107.8338
  69.5988, desktop reference frame at gt 2.6912: whole-frame mean channel
  difference 3.73 unconditional (what the site runs today) against 3.40
  conditional; pixels over 12 4.13 % against 3.73 %; bright neutral body-like
  pixels in x250-760 y430-640 2286 against 2714, desktop 2939; whole-frame
  magenta-signature pixels (r>120, b>120, g at least 40 below both) 161 against
  118, desktop 138.  Unpatched, the same port measures 4.63, 5.89 %, 2287, 108.
  The two builds now agree on every *input* to that draw -- page-side uniform
  dump against the desktop `gCycle.cpp` probe: both lights compiled, diffuse
  (1,.7,.7) and (.7,.7,1), eye-space positions (320,240,200,0) and
  (-240,-100,200,0) matching `glGetLightfv(GL_POSITION)` exactly, light ambient 0,
  model ambient (0.2,0.2,0.2), material ambient 0.2, diffuse 1, emission 0,
  shininess 0, specular 1 -- and the body still reads dark and tinted on the port,
  so the colour source was one layer of the cycle-shading gap, not all of it.  The
  remaining leads are the normal transform and the body texture path.
- `patch_light_positional.py` — the emulation always used the directional-light
  rule, `normalize(u_lightPositionN)`, which is only correct when `w = 0`.  GL's
  rule for a positional light is light-minus-vertex, both in eye space, so the
  patch now selects on `w`.  Measured: `src/tron/gCycle.cpp` is the only place
  in the tree that sets any light, and both positions carry `w = 0`
  (`lposa {320,240,200,0}`, `lposb {-240,-100,200,0}`, gCycle.cpp:4333-4334), so
  no shipped content takes the new branch.  The frame-exact A/B at n363
  (gt 2.8494, `plA` with the patch against `plB` without) differs by a fraction
  of a percent of pixels in every floor band and leaves the near field alone, so
  this is the specified rule kept for a light that does become positional, not a
  fix for the cycle shading or the far grid.  The `w = 1` rule itself was
  confirmed against the reference driver with the standalone `lightprobe.c`.

The patches assert on the code they expect and `build.sh` aborts on the first
failure, so a toolchain bump fails the build instead of shipping a page that
silently lost a fix.

## Page options

- Click the canvas for keyboard focus; ⛶ or double-click toggles fullscreen.
- The canvas backing store follows the display, not the CSS box: `innerWidth` and
  `innerHeight` are multiplied by `devicePixelRatio` (capped so the total stays
  under 4.2 Mpx) before being reported to `sr_WasmWindowResized`, the way a
  desktop framebuffer matches the physical size of its window.  Reported in CSS
  pixels, a scaled browser lights more pixels than the game draws: in a 1000x800
  client area at `devicePixelRatio 2` the canvas was 1000x601 inside a box the
  browser then stretched over 2004x1206, so a floor grid line that covers 1.4
  device pixels in a desktop window covered 0.7 here and broke into an aliased
  dotted line while the distant rows fell into a coarse mip.  The same page now
  reports 2000x1202 there, and 2560x1202 in the 1280x800 window the rest of this
  file's measurements were taken in.  Measured on the perimeter replay, floor
  grid runs (width above half maximum, as a fraction of frame width) go
  0.00442 -> 0.00559 in the near band and 0.00555 -> 0.00998 in the far band,
  with resolvable peaks in the near band 37.6 -> 62.5 per 1000 sampled columns.
  Peak-minus-median contrast falls as the runs widen (45.1 -> 26.4 near), which
  is what a properly covered line does: the light spreads over more pixels
  instead of spiking on one.  The two captures froze at recSec 8.72 and 8.89 of
  the replay, 0.17 s of play apart, and the geometry being sampled is the static
  stage grid.  At `devicePixelRatio 1` nothing is reported differently, so every
  other number in this file still holds -- they were all taken at scale factor 1.
- The in-game Display Settings menus do not offer switches a browser cannot act on.
  Screen Mode keeps Apply Changes, Check Errors, FPS Limit and Grab Mouse; Detail
  Settings keeps Floor Detail, Alpha Blending, Simple Trails and Floor Mirror;
  Performance Tweaks keeps Infinity and Swap Mode.  Removed on this platform
  (fullscreen, screen resolution, window size, colour depth, Z-buffer depth,
  vsync, dither, smooth shading, truecolor textures, the four texture filter
  groups, display lists, keep-window-active) is instead pinned in
  `sr_InitDisplay`, after the configuration has been read, to the value the
  parity measurements were taken with -- so a stale or hand-edited `user.cfg`
  cannot move the port off it, and the same is true of a player picking "Load
  Defaults" and then reloading the page.  The desktop build's menus are
  unchanged: the entries are guarded by `#ifndef __EMSCRIPTEN__`.
- `?args=--playback,/path.rec` — command-line arguments; files named by
  `--playback`/`--record`/`--playback-bench` are fetched from the web root and
  written into the virtual FS before `main()`.
  Every parity measurement in this file replays one reference recording,
  `webgl/harness/perp2.aarec` (265 KB, one single-player round, capped to 60 fps
  by `MAX_FPS`); `build.sh` copies it into the deployed site, so the published
  build can be replayed in the browser at
  `https://smarioman.github.io/armagetronad/?args=--playback,perp2.aarec`.
  Two more recordings ship the same way: `webgl/harness/perpA.aarec`, the
  no-computer-player replay behind the drift-free pair, and
  `webgl/harness/myrec2.aarec` (105 KB, two computer players, the shortest of
  the three and the quickest one to aim a browser at when checking that replay
  playback works at all).  Every recording starts with a `VERSION` section
  holding the version of the build that made it; a mismatch does not refuse the
  file, it only calls `tRecorder::ActivateProbablyDesyncedPlayback()`
  (`gArmagetron.cpp:939-950`), so a recording made by the native build of this
  tree plays in the browser build without further ceremony.
  Viewer-side settings still come from the player's own configuration; the
  published numbers were taken with `webgl/harness/autoexec.cfg`.
- `?ss=<factor>` — lift the render-target scale above the display's own pixel
  ratio: the page uses `max(devicePixelRatio, ss)`, still capped at 4.2 Mpx.
  Measured against the reference pair, `&ss=2` does not improve parity -- averaged
  back down to 1280x800 its saturated-green count in the rows 540-620 band is 0
  where the desktop has 1882, because averaging dilutes the desktop's hot
  one-pixel line rather than reproducing it.  It exists to A/B the two on one
  machine.  Below the canvas the page now prints what the browser actually
  delivered -- render target in device pixels, the scale in force, the device
  pixel ratio, multisamples, the anisotropy ceiling and the context version --
  so a report about a comparison states measured browser values instead of
  requests; the desktop build's own log says the same three things about its
  context.  Measured on the reference pair in this harness: `1280x800 px
  (scale 1, device pixel ratio 1) - multisample 0 - anisotropy up to 16 - WebGL
  1.0 (OpenGL ES 2.0 Chromium)`, and `2560x1600 px (scale 2 ...)` with `&ss=2`.
- `?proxy=wss://host/` — WebSocket bridge base for network play, remembered in
  `localStorage` (`arma_proxy_base`). Without a proxy the client tries direct
  `ws(s)://ip:port`, which the stock server does not speak, so the hosted page
  is singleplayer by default. `&mux=0` (also remembered, under `arma_mux`)
  asks the bridge for the older one-session-per-server shape instead of the
  multiplexed one; see Multiplayer below.
- User data (settings, scores, recordings) persists in IndexedDB: the page
  mounts IDBFS over `/home/web_user`. Clearing site data resets the game.
- Floor detail: the port runs the compiled-in `rFLOOR_TEXTURE`, because
  `sr_LoadDefaultConfig()` -- the "high detail defaults; no problem for your
  ordinary 3d-card" block in `rScreen.cpp` -- runs on first use only and a
  browser profile's saved config carries no `FLOOR_DETAIL` line (the port's own
  probe reports `FLOOR_DETAIL 2` with the setting never assigned), while a
  desktop install ends up on the two line textures.  Raising the wasm default to
  match was tried and measured: it came out *worse* in every band of the frame,
  so it was reverted (numbers below).  It is a normal option either way: the
  video menu, or `FLOOR_DETAIL 0..3` on the console, persisted in IndexedDB.
- The page creates the canvas' WebGL context in `preRun`, before SDL asks for
  one, because SDL 1.2 requests neither a stencil buffer nor multisampling, and a
  canvas keeps the attributes of the context created first (SDL's own
  `getContext()` then returns this same object, so the state described here is
  the state the game actually runs with).  Multisampling is deliberately off: the
  game never calls `SDL_GL_MULTISAMPLEBUFFERS`, so the desktop build has none
  either.  Forcing `antialias:true` was tried and measured on matched replay
  poses -- it cost the far floor grid 35-55 % of its contrast against the native
  build (strip luminance 16.9/10.7, 15.6/7.2, 14.6/5.8 native/wasm) and removing
  it brought the two together (16.9/15.4, 15.6/10.7, 14.6/6.9) with the grid
  periods agreeing exactly (25/25, 23/23, 21/22 px).  Anisotropic filtering is
  not forced either: the game never requests it and the desktop samples the floor
  at the GL default 1.0.  An explicit 8x pin moved the near rim wall toward the
  desktop (x 1200-1270, y 20-200, mean adjacent-pixel difference 0.494 -> 0.585
  against the desktop's 0.614) but moved the far band away from it (3.33 bright
  grid peaks per column at 13.50 peak-minus-median on the desktop, 3.33 at 13.73
  without the pin, 1.87 at 10.77 with it), and excluding the floor texture group
  changed nothing measurable, so the pin is not there.

## Visual parity against the native build

Parity is measured, not eyeballed.  A round is recorded on a native Linux build
(`--record`), the same recording is replayed on both builds (`--playback`), and
captures are taken at fixed game-time gates.  The recorder stores SDL 1.2
keysyms, the same numbers the configuration defaults, the key-name table and the
key range checks use, so the port's SDL layer converts the incoming SDL 2 events
down to them (`src/render/rSDL12KeySyms.h`, `src/ui/uInputQueue.cpp`); a
comparison build prints a per-frame stamp with game time, frame number, camera
position and view direction, so pairs are matched by pose rather than by wall
clock.

Frame counters are not a reliable key.  The current builds land within one
rendered frame of each other at game time 2.46 (341 against 342, both capped at
60 fps), but port builds from before playback was made to render every frame
reached that same game time on frame 2068 -- and the native's counter runs at
its own uncapped rate unless `MAX_FPS` is set.  A pair is therefore matched by
game-time gate and by camera pose, which measured 0.00 world units apart at
that gate, never by `n`.

The reference native run uses llvmpipe (`LIBGL_ALWAYS_SOFTWARE=1`), a software
rasterizer, which is closer to the browser's SwiftShader than to a desktop GPU
is; treat the numbers as one named reference rather than as "the machine the
player owns".  The pair below is frame-identical: both builds on frame `n331`,
game time 2.2876 against 2.2885, camera position identical to four decimals.

Grid metrics come from horizontal scan lines inside bands of the frame, given
as a fraction of frame height from the top: 0.55-0.70 is the band nearest the
horizon, 0.70-0.85 mid-distance floor, 0.85-1.00 the floor nearest the camera.
`ink` is the summed excess over the row median, `peak` the brightness a line
reaches above it, `width` the mean extent of a bright run in pixels.  The lit
rows give the share of pixels above a luminance threshold and the mean colour
of those pixels, which is where a shading error shows up directly.

along x over the 10.25 pair gives a strong peak at dy = 0, dx = -31 on the right
half of the far wall and -54 to -73 on the left half (peaks 0.35 to 0.74), while
the floor rows near the camera correlate at dx = 0 with peak 0.90: the floor and

claimed the best global shift was (0,0); that searched only +-30 px and fitted a
single shift to the whole frame, and was wrong.  The displacement is the replay
diverging, not the drawing: the port prints

    AI timing decision changed by 1 from 1 to 0!
    AI turn decision changed!

from `gAIPlayer::ActOnData` (`src/tron/gAIBase.cpp:2906-2928`), which compares
the locally recomputed AI decision with the recorded one; the desktop run of the
same recording never prints either.  The two builds' `sinf` agree bit for bit on
15 sample arguments and a 40-step double-precision `sin` loop reproduces
exactly, but a 40-step *float* `sinf` loop ends one ulp apart (0.259053379
against 0.259053409): glibc and the emscripten libm are not the same
implementation, and a cycle-physics simulation amplifies one ulp per call into
metres over ten seconds of play.  AI trails therefore differ between the two
playbacks, and whole-frame scores at the later gates measure that, not the GL
stack.  Parity measurement has to be read gate by gate and weighted to the early
ones, where the pose still agrees to 0.01 world units and the shipped set scores
1.11: it is the near field -- floor, cycles, the wall the camera is facing --
that is comparable, and the gates past 10 are only useful for spotting gross
errors.  Pinning the far band down properly would need the simulation made
bit-identical first, which is out of reach; the vertex data each build hands to
GL (the port's page-side hook captures it, the desktop side needs an `LD_PRELOAD`
shim) is the way to settle any residual rendering difference on the early gates.

### A pair without simulation drift

The note above treats bit-identical simulation as out of reach.  What drifts is
the computer players, whose decisions get recomputed locally and compared with
the recorded ones (`gAIBase.cpp:2906-2928` prints the mismatch).  Take them out
and the two playbacks stay in one world.  `webgl/harness/perpA.aarec` is a
lone-cycle round -- `SP_NUM_AIS 0`, `SHOW_HUD 0` and `DITHER 0` so the help

cycle lives to the far end of the arena -- recorded on the desktop and replayed
by both builds under `webgl/harness/autoexec_clean.cfg`.  Gated on game time,
the desktop lands at gt 5.0160 / 10.0000 / 16.0668 and the port at 5.0003 /
9.9670 / 16.0336, with the stamped camera 0.47, 0.99 and 0.99 world units apart
at the three gates, and identical x, heading and height.

and 1.96 at the other two.  Pixels differing by more than 30: 0.03 %, 0.08 %,
0.19 %.  More than 60: 0.01 %, 0.02 %, 0.04 %.

Texture data is not the cause of the far-grid residual.  The uploaded level-0

[1,1], anisotropic extension present and left at 1.0 on both sides.

Three levers aimed at the far-grid residual, measured on this pair, all
rejected.  Un-mipmapped sampling (`GL_LINEAR` as every min filter, page side)
puts 2347 pixels above luma 16 in the far band against the desktop's 247, and
grows the mid band by 4446 pixels above luma 40 where the desktop has 206:
moire, not detail.  Four-times anisotropic sampling on every texture lifts the
east-west amplitudes to 1.67x the desktop's and the north-south family to 15.80
against 13.57, overshooting a reference that samples at 1.0.  The analytic

moves whole-frame agreement from 0.45 to 2.57; it confirms the decision recorded

pair that does not drift.

What remains is the rasterizer's own level estimate: ANGLE over SwiftShader
samples the far half of the east-west family about a third of a mip level
coarser than llvmpipe, from the same coordinates, the same mip chain and the
same blend.  GLSL ES 1.00 offers no sampler bias, and the explicit-LOD route
that would pin the level down measures as a net loss, so the shipped build
keeps ANGLE's choice.

### Reproducing the comparison

The recording used for this is `webgl/harness/perp2.aarec`: a single-player
round on the default map, 60 fps capped, with the camera driven around the
perimeter of the stage, so walls, floor and cycles all appear edge-on and
head-on.  The native build is configured with the same `autoexec.cfg`
(`webgl/harness/autoexec.cfg`) and played back under Xvfb:

    src/armagetronad_main --norun --loglevel 4 \

`--playback FILE` takes the file as a separate argument, not joined by `=`.
Keystrokes are sent with `xdotool`; the menu sequence that starts a single
player round is `w:4500 e:1500 d:700 e:1500 e:1500` (wait, then Enter).  A
comparison build prints one line for every rendered frame:

    FRAME <n> state 6 gt <game time> ncam <c> pos <x> <y> h <h> dir <dx> <dy>

The port writes the same line to `stdout` (the browser console); the native
writes it to `stderr`.  `webgl/harness/cdpd.py` drives the port over the Chrome
DevTools protocol: it watches that stream, fires a screenshot when the step
condition is met (`N:341,s` grabs at frame 341) and writes `<tag>-NN.png` plus a
`<tag>-shots.txt` manifest line carrying the pose.  `webgl/harness/glinstrument.c`
is an `LD_PRELOAD` interposition for the native build that counts draw calls per
primitive mode and prints the projection matrix, which is how the two builds'
command streams were compared.  The analysis tools take those manifest lines on
stdin (`png rect tag gt pos dir`): `gridprofile.py` profiles the grid lines per
band, `parity_report.py` reports window peak, coverage and row profile, and
`modelshape.py` extracts the light-cycle silhouette and `cyclegrid.py` reports
the luminance spread of the cycle crop together with the line peaks of a fixed
floor band.

Two more things decide whether a pair is comparable at all.

The build's version string has to match the recording's.  A client that reads a
different one says so and switches to "probably desynced" playback, which
relaxes the cycle-movement replay match and takes a different time-archive path:
the two builds then run different replay logic while looking identical.  That
string comes from `batch/make/version` -- commit count, plus a date suffix while
the tree is dirty -- so it moves with every commit, upstream merges included.  A
comparison build therefore pins `src/nTrueVersion.h` to the recording's value and
touches it after configure, which stops the make rule at `src/Makefile.am:30`
from regenerating it; both trees are then identical in that respect.

The screenshotted frame is the last one composited, not the one the stamp line
described, so the same binary captured twice at the same game-time gate can
differ.  Measured: one build captured twice at the five gates of the reference
recording gives 9.10, 0.00, 30.73, 1.29, 6.85 (mean 9.59).  A whole-frame score
is only meaningful against that spread.  Replaying `webgl/harness/perp2.aarec`
on a build with `v0.2.9.3.1` merged scores 4.58, 10.67, 33.63, 9.28, 9.45 (mean
13.52) where the pre-merge build scored 1.11, 10.67, 36.27, 9.25, 9.57 (mean
13.37): the same result, inside the noise.  Three of the five desktop captures
before and after that merge are pixel-identical, and two of the port's are.

Two stamp variants have been in use and their manifest fields are not the same
numbers: `webgl/harness/parity-stamp.patch` reports `CameraPos()` and
`CameraZ()`, while a `grid->CameraGlancePos(i)` / `grid->CameraHeight(i)` probe
reports the eye position and its height above the target.  Gates parse `gt` by
name and are unaffected, but pose deltas taken across the two variants mean
nothing.

### What a matched pair does and does not pin down

Computer players used not to be reproducible.  The AI draws its randomness from
`tRandomizer::GetInstance()` (`gAIBase.cpp:96,119`), which called the C
library's `rand()`; that generator was seeded from the wall clock at
`ePlayer.cpp:1132` and nothing archived its draws, so each build drove its own
computer players.  Measured on the reference recording before the change: the
builds agreed on the camera to 0.04 world units at gt 2.6 but were 4.3 and 5.6
units apart by gt 4.6 and 6.5, the camera having switched to a computer player
running its own random path.  Every replay generator is now seeded from its own
archive section and numbered by position inside that section, so both builds start a
replay world from the same numbers -- but they do not stay in it.  Measured on
`perp2.aarec` with ten computer players and `MAX_FPS 60` on both sides, 1363 paired
stamped frames: every cycle agrees to 0.04 world units or less right up to gt 1.86,
then the first computer player's cycle leaves the other build by 0.72 units at gt 1.88
and by 44, 63, 97 and 131 units (cycles 3, 5, 7, 9) at gt 8.40, while cycle 13 exists
only in the desktop run and cycle 17 only in the port's.  The cause is the math
library, not the seed: the desktop links glibc's libm, the browser build musl's, and a
probe printing 288 function values as hex doubles disagrees on 6 of them -- 1 ulp on
`atan2` twice and on `cos` once, 2 ulp on `tanf` three times (0x1.6e3d06p+1 against
0x1.6e3d04p+1).  AI steering is float arithmetic through exactly those functions, so a
comparison threshold flips and the two worlds part company a second and a half into the
round.  Nothing port-side can undo a different libm, so the protocol is to gate a pair
while the world is still provably shared (gt < 1.9 on this recording), or to restrict
the comparison to geometry that does not depend on where the computer players have
wandered.  A pair's `gt` fields are not comparable either: the two game clocks sit
about 0.09 s apart on this recording whatever the gate asks for, which is why the
harness drives the port by pose.

A matched pair is still not bit-identical in pose.  Measured on the current
builds at frame 323 (desktop gt 2.1486, port gt 2.1495): all four live cycles
agree exactly on heading and to 0.026 world units on position, which is exactly
cycle speed 20 units/s times the 0.9 ms the two game clocks sit apart at that
frame.  One of the four has died on both builds by frame 373, the same one.  A
sub-millisecond clock offset is invisible on a body but not on a line: it moves
a distant wall or floor grid line by a pixel or two, so a per-pixel difference
image taken over thin far structures is not evidence about the renderer, while
the band statistics (peak height, lit-run width, line counts per row) are.

`ppR0-00`), mean luminance / pixels over 150 / pixels over 240 in fixed boxes:

### Cycle geometry the emulation mis-sizes

The chat pyramid painted a wedge of the player's colour across the view.  Its
two triangles went through the immediate-mode path, where the legacy GL
emulation derives the submitted vertex count by dividing by one uniform
per-vertex stride: a vertex of this primitive costs three position floats plus
four colour floats, so the six-vertex batch is counted as 5.2 and only five
reach `drawArrays`; the rasterised triangle then takes a corner from the wrong
record.  Measured on the frame-exact n280 pair, mean luminance 24.0 in the
40x355 band the wedge covers against the desktop's 3.11, with about 3.7k extra
lit pixels.  The same six corners and two colours now go through
`atglDrawArrays`, the client-array route the cycle shadow already uses, and that
band measures 3.13 against the desktop's 3.11.  The desktop keeps its original
immediate-mode calls (`src/tron/gCycle.cpp:4542-4554`).

The headlight fan is latent rather than an observed difference: `USE_HEADLIGHT`
is commented out at `src/tron/gCycle.h:31`, so neither build draws it today.  It
is guarded on the port for the day the feature is enabled: the fan's radial
falloff comes from a `GL_ARB_fragment_program`, which the fixed-function
emulation has no equivalent of, so the fan -- outer vertices at each sensor's
hit point, up to `arena_size*500*sqrt(2)` away, drawn additively with `GL_ONE,
GL_ONE` and no depth write -- would arrive flat and fully bright and lay a solid
wedge of every cycle's colour over the floor, the walls and the cycles in front
of the camera.  Giving the port that light pool needs the falloff expressed as a
texture.

### Comparison instrumentation

Captures are paired by the parity stamp: a block in `gGame::Render` printing the
line quoted above once per rendered frame, the port writing it to `stdout`
(the browser console) and the native build to `stderr`.  The block is not part of
the published tree -- a shipped build should not carry instrumentation the game
never asks for, however cheap its guard -- and a capture session puts it back
with

    git apply webgl/harness/parity-stamp.patch

`webgl/harness/cdpd.py` keys its gates off the five characters ` FRAME ` -- hence
the `PF` prefix -- and reads the fields by name (`gt`, `pos`, `h`, `dir`) from
whatever follows, which is what fires a screenshot at the same game time on both
builds.  A build without the block can only be driven on wall-clock waits, never
on game time.

The taps used while tracking the divergences are working-tree only for the same
reason: an event tap in `EventArchiver::Archive`, which is what exposed the
SDL 1.2 against SDL 2 keysym mismatch in replayed input; a texture-upload tap in
`rTexture.cpp`; a wall-pass tap in `gWall.cpp`; spark taps in `gSparks.cpp` and
`gCycle.cpp`; and a GL-error tap around every `glDrawArrays` in the
client-array helper.  Page-side hooks - `getContext` wrappers logging GL state
or a draw census - are written into `webgl/dist/` by hand and referenced from
the generated `index.html`; `webgl/build.sh` wipes `dist/` on every run, so they
are applied after the build and never committed.

One instrument needs no working tree: `webgl/site/lodtest.html` draws a single
grazing floor plane four times, each quarter resolving the floor texture's mip
level differently -- the driver's own `texture2DProj` rule, which is what the
game emits, because the fixed-function texture environment compiles every
textured draw into a projective sample -- an explicit level from the divided
coordinate's gradients, one from the un-divided gradients, and a plain
`texture2D` reference -- and then measures its own result: far band contrast,
lit pixels in the distance band, near band contrast, printed under the canvas.
On the capture stack used here (Chrome / SwiftShader) all four agree at
6.5 / 16.7 / 10.4, which is why no sampler-level patch ships: on that hardware
the projective call is demonstrably not what thins the distant grid.  Run it on a
machine where the grid does thin out; if there A sits below D, the level
computation is the mechanism and the port has to pin the level instead of
delegating it to the driver.

### Grinding sparks

`gSpark` draws one line segment per grinding contact, from the contact point
along the drive direction, `ago * 0.8 * |xDot|` long, where `ago` is the
difference between the current time and the moment the shower was created
(`tron/gSparks.cpp`). On the port that difference was taken against the render
clock while the shower is created on the simulation clock, and the port steps
the simulation in several fixed steps per animation frame, so the render clock
lags and the segment came out long: the streaks read as stretched along one
axis. The port now uses the simulation clock for the difference and clamps the
span (`d7e543c8`), which brings both builds into the same range -- measured over
the sparks alive in a frame, the segment-span histogram tops out at 0.474 world
units on both and both show the same pile-up at the clamp.

Two facts matter for anyone trying to reproduce the symptom. A shower is only
created while the cycle is *turning* in wall contact: both spawn sites sit
inside `if (fabs(skew) < fabs(lr*.8))` and `.9` gates (`tron/gCycle.cpp:3123`,
`3146`) together with `crash_sparks && sparkts > 0`, so a cycle sliding straight
along a wall -- which is what a straight-line perimeter replay does -- creates
none at all; the earlier grinding replays that reported zero showers were
measuring that, not the renderer. And with the world standing still (a harness
build that can skip the spark layer, and separately freeze the simulation while
the render loop keeps running, both working-tree only in `gGame.cpp` and
`gSparks.cpp`), suppressing the layer on the desktop changed no pixel by 12 or
more in the region the stream projects into; the differences that did appear sat
in the on-screen message band far from it, and a second frozen pair differing by
3.7 ms of game clock differed by zero pixels across the whole frame. On the
current builds there is no stretched-spark signature left to chase.

## Gamepad support

A standard Gamepad-API pad drives the cycle with no player setup
(`src/ui/uInputQueue.cpp`, `atPollPad`). The sample is taken in JavaScript and
copied into the wasm heap through `Module.HEAPU8`/`HEAPF32` - which is why the
link line exports those runtime views - and every change of pad state becomes an
ordinary SDL 1.2 key event inside the input pump: the keymap, the menus, the
netgame protocol and `.aarec` archives see key presses and never learn that a
pad exists.

Two mapping layers, so that the pad cannot collide with the keyboard:

- The d-pad and the two face buttons used in menus post real key numbers
  (arrows, SPACE, ESCAPE). Menus and in-game behaviour then follow whatever
  keyboard layout the player chose, with nothing to configure.
- The two sticks and the remaining buttons post private numbers (`SDLK_PAD_*`,
  `src/ui/uInput.h`, kept above `SDLK_NEWLAST` so that no keyboard and no
  archive can produce one). `atAddPadDefaults()` binds those to cycle actions:
  left stick and both bumpers turn, both triggers brake, Y toggles the brake, X
  looks back, the left stick click switches the camera, the right stick moves
  the camera, Back shows the score and Start opens the in-game menu. The right
  stick click and the left stick's up and down stay unbound: the cycle
  accelerates by itself and this game has nothing sensible for them to do.

That pass runs once per configuration, tracked by `GAMEPAD_DEFAULTS_ADDED`,
which is a version rather than a flag: port builds up to 2026-11-13 numbered the
private keys from the SDL layer's own `SDLK_LAST` and wrote those numbers into
the user configuration, so such a player has to be given fresh bindings instead
of being left with dead key numbers. A key number that is already bound is never
overwritten, so a deliberate rebind survives. `GAMEPAD_SUPPORT 0` stops the
polling; a pad whose sample throws (no Gamepad API, or a heap view left detached
by a memory growth) disables the pad driver after a few failed reads rather than
taking the input pump down with it. Chrome attaches a pad to the page only after
the first input gesture, so a player has to touch a key or button once.

Measured on the page against a scripted standard pad, with the game clock
stepped frame by frame: an 11-frame left-stick-right hold moves the cycle
heading -77.8 deg and the matching left hold brings it back +77.6 deg, the pair
reproducing across a rebuild; holding the d-pad left turns +86 deg, and the
recorded menu path navigates on the d-pad unchanged. One trap found while
measuring: the recorded menu path presses ENTER during the round countdown,
which opens the chat line, and while the chat line is open the game ignores
cycle input - the heading then looks frozen even though every pad event is
arriving.

## Multiplayer

Browsers cannot send UDP, and Armagetron's protocol is UDP, so network play
needs the bridge in `webgl/proxy/`:

```sh
cd webgl/proxy && npm install
PROXY_PORT=8091 node proxy.js                       # ws://
TLS_CERT=... TLS_KEY=... PROXY_PORT=8443 node proxy.js   # wss://
```

Then open the game page with `?proxy=ws://host:8091/` (or
`?proxy=wss://host:8443/`); an https deployment requires `wss://`, or the
browser blocks the connection as mixed content. **One** bridge session then
carries every server the client talks to: each datagram travels with a 9
byte header naming the peer it belongs to -- an address or a host name, and
names are resolved by the bridge because the browser cannot resolve them --
and answers come back with the same header naming the sender. A bridge that
predates that format gets the old shape instead, one WebSocket per
`(server,port)`; `?mux=0` asks for the old shape explicitly.

Many players share one bridge address, and an Armagetron server counts
queries per source address (measured: "Flood protection bans 127.0.0.1 after
10 pings in 0.81 seconds"), so the bridge meters what it relays. A
destination starts on a discovery budget (default 6 datagrams/s, burst 8)
and is lifted to a game budget (60/s) once the volume coming back from it
proves a live session rather than a poll. `GET /status` on the same port
reports the open sessions, their counters, and lifetime totals including
what had to be delayed or dropped. `ALLOW=host[,host:port]` restricts which
servers the bridge will talk to; unset means any host, which makes the
bridge an open UDP relay, so set it before exposing it to the Internet.

This path is not covered by CI. It was verified against a native dedicated
server of the same version running next to the dev site: a LAN sweep, the
server list, a login and three full rounds over one multiplexed session,
with the server's flood protection left at its shipped setting and zero bans
(the same run in the per-destination shape needed 13 sessions).

`node webgl/proxy/selftest.js` runs the bridge's own regression test: it starts
a bridge and a one-socket UDP server on spare ports and plays the part of the
wasm client. It checks that the very first datagram to a named destination
actually arrives, that the answer comes back labelled with the name the client
used rather than with the address the bridge resolved, that a name which does
not resolve is reported instead of killing the bridge, and that `/status` lists
the peers. The first check is the one that used to fail: the destination entry
is created by an asynchronous lookup, so the datagram that created it always
beats it to the socket, and a bridge that discards what it cannot send yet loses
the first query to every named server.


Join from the menu: Play Game → Multiplayer → Custom Connect (or a Server
Bookmark) and give the address and the port of the server. The login
handshake and the two sync rounds of a join are stepped one iteration per
animation frame (`sn_ConnectPump`, `sn_SyncStart`/`sn_SyncStep`) because the
browser only delivers the server answer while the frame function is off the
JS stack.

### Server browser

Both browse modes work through the bridge; the blocking native browse loops
are stepped per animation frame instead (`nServerInfo::PumpBrowse()`, called
from the browser menu's redraw).

- *Online Multiplayer* talks to the master servers in the master list: the
  list is `config/master.srv` from the data bundle plus every
  `ADD_MASTER_SERVER <name> <port>` (config file or console). Master names
  are resolved by the bridge. The connect, the list request and the answer
  collection all run on the frame clock; a master that does not answer is
  retried, then the list is sorted and shown.
  The detailed information (ping, user count, game name) comes from a second
  round, one direct query per listed server (`DoQueryAll`, bounded by
  `BROWSER_QUERIES_SIMULTANEOUS` and by the game's own per-server query budget).
  The menu arms that round when it opens, which on this platform is before the
  master answer has been collected, so the round walks an empty list and marks
  itself finished; the menu's redraw (`RenderBackground`, which already calls
  `PumpBrowse`) therefore re-arms it every time a browse round finishes, the same
  call its refresh key makes. Measured over one master round on the live master:
  before the re-arm, zero direct queries and one bridge peer; after, 40 queries
  and 12 peers with 153 datagrams back, every row showing ping and users.
- *LAN Multiplayer* sends a `RequestSmallServerInfo` broadcast to ports
  4534-4540, one port per 0.25 s. Over the multiplexed session the whole
  sweep runs on that one socket: the bridge turns each sweep datagram into a
  real UDP broadcast and labels every answer with the answering server,
  which is what lets the client query and join the servers it just
  discovered. In the per-destination fallback each port is its own session
  and the bridge prefixes answers with 4 byte address plus 2 byte port
  instead. Hosts a broadcast cannot reach (separate machine, loopback) are
  added with `LAN_EXTRA=host[:port][,host[:port]]` on the bridge: every
  sweep datagram is replayed to them as a unicast.

## Limitations

- No background music: the SDL1 JS port has no mixer, so only sound effects
  play.
- The toolchain is pinned (`webgl/SDK_VERSION`) because the build depends on
  `-s LEGACY_GL_EMULATION=1`, which newer emscripten releases are phasing out.
- Single-threaded: no pthreads/SharedArrayBuffer, so no COOP/COEP requirement.
- Network play needs the bridge, as above.
- LAN server browse only sees what the bridge's own network can reach: the
  broadcast leaves from the bridge host, not from the browser's network.
  `LAN_EXTRA` on the bridge covers hosts that broadcast cannot reach.
- Frame rate is bounded by the fixed function emulation (every immediate mode
  call is re-tessellated in JS) and by the browser's software renderer when no
  GPU is available. Measured in headless Chrome with SwiftShader: menus run at
  ~60 frames/s, a round at ~1.6 frames/s. The HUD `FPS:` readout and the game
  clock both follow that rate correctly, so a low number is the renderer, not a
  broken timer.
- The top level main menu cannot be left. The native build exits the process
  there; a page has no process to exit into, so leaving that menu re-opens it
  and its "Exit game" item is not shown.
- No cycle headlight pool.  The feature is off in the game itself
  (`USE_HEADLIGHT`, commented out at `src/tron/gCycle.h:31`); if it were
  enabled, the port would need its radial falloff expressed as a texture,
  because the desktop gets that falloff from a `GL_ARB_fragment_program` the
  fixed-function emulation cannot express and an unguarded port fan would paint
  flat and fully bright.

## Deployment

GitHub Pages must build from Actions (repository **Settings → Pages → Build and
deployment → Source: GitHub Actions**). Then a push to `webgl` runs
`WebGL build & Pages`: it builds the toolchain, bootstraps autotools, builds
the wasm, uploads `webgl/dist/` as a Pages artifact and publishes it at
<https://smarioman.github.io/armagetronad/>. Pull requests to this branch build
and keep the site build checkable but do not deploy.
