# Armagetron Advanced in the browser (WebAssembly + WebGL)

The `webgl` branch runs Armagetron Advanced 0.2.9.3.0 as a WebAssembly module
in the browser: SDL1 through emscripten's JS port, the game's fixed-function
OpenGL pipeline through emscripten's legacy GL emulation, and every data file
preloaded into the virtual filesystem.

Live site: <https://smarioman.github.io/armagetronad/>. Every push to this
branch rebuilds the game and republishes that site automatically
(`.github/workflows/webgl-pages.yml`).

## Branch lineage

`webgl` branches from the `v0.2.9.3.0` tag (`036daaf3`), which sits on
`trunk`'s history: the port builds on that release, with SDL1 through
emscripten's SDL1 port, the release's own autotools build, and its UDP netcode.

`trunk` has moved on to 0.4 development - SDL2 + protobuf, 666 files under
`src/` changed against 0.2.9.3.0 - so this branch deliberately does not carry
those commits: the port is not a patch set for that tree, and mixing the two
leaves a source tree that neither the 0.2.9 nor the 0.4 build system can
configure.  Giving 0.4 a web build means re-applying the same design there -
the WebSocket transport in `nSocket.cpp`, the event-loop frame driver, the three
generated-JS patches, building the `resource/` maps before the link - as new
work.

## Layout

| path | purpose |
|---|---|
| `webgl/build.sh` | configure + make + post-build JS patches, then assembles `webgl/dist/` |
| `webgl/setup_toolchain.sh` | installs the pinned emsdk and cross-builds libxml2 for wasm |
| `webgl/SDK_VERSION` | the emsdk version this port is pinned to |
| `webgl/emscripten.cache` | autoconf cache for the wasm cross-configure, generated by `build.sh` |
| `webgl/patch_*.py` | post-build fixes applied to the generated JS (see below) |
| `webgl/site/index.html` | the player page; copied into `webgl/dist/` |
| `webgl/serve.py` | local static server for `webgl/dist/` |
| `webgl/proxy/proxy.js` | WebSocket↔UDP bridge so the client can reach real servers |
| `webgl/dist/` | build output (gitignored) — this is what gets deployed |

## Building

Prerequisites: `git`, `curl`, `python3`, `make`, `g++`, `autoconf` ≥ 2.69,
`automake` ≥ 1.16, `pkg-config`. Network access is needed for the toolchain
download.

```sh
./webgl/setup_toolchain.sh   # emsdk (webgl/SDK_VERSION) + libxml2 for wasm
./bootstrap.sh               # regenerate configure / Makefile.in
./webgl/build.sh             # wasm build  -> webgl/dist/
./webgl/serve.py             # serve on http://127.0.0.1:8080
```

Environment knobs: `EMSDK_DIR`, `LIBXML2_PREFIX`, `SDK_VERSION`,
`DOWNLOAD_DIR`, `JOBS`, `CLEAN=0|1`, `PORT`.

There is no emscripten port of libxml2, and the resource manager needs it to
parse the XML resources, so `setup_toolchain.sh` cross-compiles libxml2 2.9.14
as a static library. `webgl/build.sh` runs configure with
`--host=wasm32-unknown-emscripten`, a cross-compile cache
(`webgl/emscripten.cache`) and `-D` overrides that point every install path at
the preload root; the native build is untouched.

## What was changed in the game

Wasm-specific code sits in new files or inside `#ifdef __EMSCRIPTEN__` blocks,
so native builds compile and behave exactly as before.

| area | change |
|---|---|
| `src/tools/tWasmLoop.{h,cpp}` | The blocking frame loops (`while (OnFrame()) {}`) are driven from the JS event loop via `emscripten_set_main_loop`. Nested loops, exit actions and continuations are supported; `main()` hands over to the event loop at the first loop and never returns, so the startup chain (language menu → first setup → main menu) is re-entered as steps (see `src/tron/gArmagetron.cpp`). Asyncify was deliberately not used: re-entering `main()` re-runs initialization and desyncs input. |
| `src/network/nSocket.cpp` | The browser has no UDP sockets, so each `(ip,port)` destination becomes one binary WebSocket session: proxy mode `<Module.ARM_PROXY_BASE>?target=<ip>:<port>`, direct mode `ws(s)://<ip>:<port>`. One WebSocket message is exactly one Armagetron datagram; datagrams sent while a session is still opening are queued and flushed on open. |
| `src/render/rScreen.cpp` | Display init for a canvas that follows the window: `sr_WasmWindowResized(w,h)` (exported) re-inits the display for the "desktop" screen mode; GL context/attribute handling for WebGL. |
| `src/render/rEmscriptenGLU.h` | GLU is not available in the emscripten GL stack: `gluPerspective`, `gluLookAt`, quadric/mipmap helpers reimplemented on plain GL. |
| `src/render/rSysdep.cpp`, `rGL.*`, `rDisplayList.cpp`, `rViewport.cpp` | Single-buffered WebGL swap (skip the color-buffer clear that would wipe the frame), `GL_QUAD_STRIP` handling, display-list limits, texture unit state. |
| `src/render/rTexture.cpp` | Image loading reads the file from the virtual FS (`fread` + `IMG_Load_RW`); the alpha convention matches native SDL_image, so no `IMG_InvertAlpha`. |
| `src/engine/eSound.cpp` | The SDL1 JS port has no `SDL_LoadWAV`, so a small RIFF/WAV parser loads effects; the mix callback buffer is explicitly zeroed (the JS port reuses one buffer, which otherwise accumulates samples forever). No music mixer. |
| `src/engine/eTimer.cpp`, `src/tools/tSysTime.*` | Frame timing and the clock driven from the animation-frame cadence. |
| `src/tools/tDirectories.cpp`, `tResourceManager.cpp`, `tConfiguration.cpp` | No binreloc in the browser: paths resolve to the preload root, user data to `$HOME/.armagetronad/var` (mounted as IndexedDB by the page). |
| `src/ui/uMenu.*`, `uInput*.cpp` | Menu rendering/keyboard handling for the event-loop model and browser focus rules. |
| `src/tron/*` | Startup sequence, splash/logo handling, server browser/favorites for the transport change. |
| `src/ui/uInputQueue.cpp` | The event archiver stores SDL 1.2 keysyms; the runtime delivers SDL 2 ones. A generated table translates the 56 keys whose numbers differ, in both directions, so replays drive the menu and the throttle arrows reach the game. |
| `src/tools/wdbg.h` | Console logging that compiles to nothing unless the build adds `-DWASM_DBG`. |

## Post-build JavaScript patches

emscripten generates JS that the game cannot use as-is; `webgl/build.sh` runs
these patches on `src/armagetronad_main.js` after every link:

- `patch_sdl_convert.py` — `SDL_ConvertSurface` calls `drawImage(null)` on
  surfaces whose 2D canvas `IMG_Load_RW` discarded in `SDL.GL` mode; falls back
  to a heap-buffer copy. Without it the game froze on the first game start.
- `patch_gl_emulation.py` — the legacy GL emulation lacks immediate-mode
  `GL_QUAD_STRIP`, used for player walls; the mode is retargeted to
  `GL_TRIANGLE_STRIP`, which the wall's vertex order already is.
- `patch_emulation_fixes.py` — the fixed-function fragment shader is hardcoded
  to `precision mediump float`, which bands fog, trail fades, floor lighting
  and per-vertex wall alpha on desktop WebGL; promoted to `highp`.
- `patch_texture_projective_coords.py` — the emulation samples textures with
  `(textureMatrix * texCoord).xy` and discards the coordinate's fourth
  component, but the infinite floor and sky planes in `src/engine/eDisplay.cpp`
  encode their perspective falloff in exactly that component (`glTexCoord4f`
  with `w=1` at the near vertex, `w=0` along the rim), so the falloff those
  planes encode in that component was being dropped.  Whether that alone
  changes the picture is a separate question from conforming to the spec; the
  shader text the running page emits is the way to check any of these took
  effect.
- `patch_light_colormaterial.py` — desktop GL enables `GL_COLOR_MATERIAL` by
  default, so a cycle's per-vertex colours *are* its material ambient and
  diffuse; the emulation lights the raw material state instead. In
  `src/tron/gCycle.cpp` that material is plain white, so the two lights next to
  the bike blew the body out to flat saturated yellow and flattened its shading
  gradient. Ambient and diffuse now come from the vertex colour; specular stays
  on the material, which is what colour material leaves alone.
- `patch_light_positional.py` — the emulation always used the directional-light
  rule, `normalize(u_lightPositionN)`, so the two lights `src/tron/gCycle.cpp`
  places next to the bike (`w = 1`, default constant-only attenuation) were
  pointed from the eye-space origin instead: whatever faces the camera got lit
  and the lamps' actual position was ignored.  The lighting pass runs in eye
  space, so the positional form is light minus `ecPosition`.  The half-vector
  is left as emitted, because GL's default is the headlight eye vector.

The patches assert on the code they expect and `build.sh` aborts on the first
failure, so a toolchain bump fails the build instead of shipping a page that
silently lost a fix.

## Page options

- Click the canvas for keyboard focus; ⛶ or double-click toggles fullscreen.
- `?args=--playback,/path.rec` — command-line arguments; files named by
  `--playback`/`--record`/`--playback-bench` are fetched from the web root and
  written into the virtual FS before `main()`.
- `?proxy=wss://host/` — WebSocket bridge base for network play, remembered in
  `localStorage` (`arma_proxy_base`). Without a proxy the client tries direct
  `ws(s)://ip:port`, which the stock server does not speak, so the hosted page
  is singleplayer by default.
- User data (settings, scores, recordings) persists in IndexedDB: the page
  mounts IDBFS over `/home/web_user`. Clearing site data resets the game.
- Floor detail: the port runs the compiled-in `rFLOOR_TEXTURE`, because
  `sr_LoadDefaultConfig()` -- the "high detail defaults; no problem for your
  ordinary 3d-card" block in `rScreen.cpp` -- runs on first use only and a
  browser profile's saved config carries no `FLOOR_DETAIL` line (the port's own
  probe reports `FLOOR_DETAIL 2` with the setting never assigned), while a
  desktop install ends up on the two line textures.  Raising the wasm default to
  match was tried and measured: it came out *worse* in every band of the frame,
  so it was reverted (numbers below).  It is a normal option either way: the
  video menu, or `FLOOR_DETAIL 0..3` on the console, persisted in IndexedDB.
- The page creates the canvas' WebGL context in `preRun`, before SDL asks for
  one, because SDL 1.2 requests neither multisampling nor a stencil buffer: the
  context comes up with `antialias:false, stencil:false` and every 1 px light
  cycle line is then an unantialiased staircase that reads as a chain of
  separate rectangles. The same hook enables
  `EXT_texture_filter_anisotropic` and sets up to 8x anisotropy on every
  texture the game uploads; with only isotropic mipmaps one screen direction
  stays under-sampled and the minified floor grid moires badly toward the
  horizon. A desktop build gets both from the driver, so this restores parity
  rather than adding detail. The extension state and the buffer attributes
  belong to the context created first, and SDL's own `getContext()` call
  returns this same object.

## Visual parity against the native build

Parity is measured, not eyeballed.  A round is recorded on a native Linux build
(`--record`), the same recording is replayed on both builds (`--playback`), and
captures are taken at fixed game-time gates.  The recorder stores SDL 1.2
keysyms, which the port's SDL 2 event layer has to translate
(`src/ui/uInputQueue.cpp`); both builds print a per-frame stamp with game time,
frame number, camera position and view direction, so pairs are matched by pose
rather than by wall clock.

Frame counters are not comparable across the two builds: the port plays the
recording at up to twice the recorded rate because its clock advances faster, so
a pair is matched by game-time gate and by pose (typically within 0.1 world
units), never by `n`.

The reference native run uses llvmpipe (`LIBGL_ALWAYS_SOFTWARE=1`), a software
rasterizer, which is closer to the browser's SwiftShader than to a desktop GPU
is; treat the numbers as one named reference rather than as "the machine the
player owns".  The pair below is frame-identical: both builds on frame `n331`,
game time 2.2876 against 2.2885, camera position identical to four decimals.

Grid metrics come from horizontal scan lines inside bands of the frame, given
as a fraction of frame height from the top: 0.55-0.70 is the band nearest the
horizon, 0.70-0.85 mid-distance floor, 0.85-1.00 the floor nearest the camera.
`ink` is the summed excess over the row median, `peak` the brightness a line
reaches above it, `width` the mean extent of a bright run in pixels.  The lit
rows give the share of pixels above a luminance threshold and the mean colour
of those pixels, which is where a shading error shows up directly.

The table describes the published build before the fixes listed below; the
current numbers are in the closing part of this section.

| | native | port as published | port + floor 3 (reverted) |
|---|---|---|---|
| horizon ink / peak / width | 9744 / 152 / 4.8 | 6135 / 103 / 3.4 | 4841 / 73 / 2.7 |
| mid ink / peak / width | 17439 / 195 / 4.5 | 14805 / 194 / 7.4 | 15559 / 172 / 6.5 |
| near ink / peak / width | 2293 / 86 / 2.1 | 1478 / 32 / 4.8 | 1330 / 22 / 1.7 |
| crossings per scan line | 15.6 / 17.7 / 7.4 | 16.2 / 10.3 / 7.2 | 23.4 / 12.0 / 21.4 |
| lit >128 %, mean R/G/B | 3.89 / 109,224,101 | 3.17 / 171,208,132 | 3.13 / 173,208,134 |
| lit >64 %, mean R/G/B | 11.75 / 91,130,80 | 12.37 / 94,124,79 | 12.12 / 95,124,80 |

Measured from inside the running game, on both builds: the floor's texture
object carries `GL_LINEAR_MIPMAP_LINEAR` / `GL_LINEAR`, `GL_CLAMP_TO_EDGE` on
both axes, and `GL_TEXTURE_MAX_ANISOTROPY_EXT = 1.0` -- the desktop build's own
floor texture reports the same four values, so neither side ever asks for
anisotropic filtering (`src/` contains no multisample or anisotropy request at
all). The browser context itself reports `SAMPLES 0`, `SAMPLE_BUFFERS 0` (the
page does request `antialias: true`; SwiftShader does not deliver it),
`ALIASED_LINE_WIDTH_RANGE` 1..1 and max texture size 8192. An earlier revision
of this file listed 4 sample buffers and 8x anisotropy in use; both figures are
now contradicted by the direct measurements above.

What has been closed since that table was written:

- The wall's bright top edge.  The desktop never sets a texture coordinate for
  it: the line inherits the previous wall quad's last texcoord and therefore
  samples the bright edge of the wall texture.  The port's GL emulation gives an
  immediate-mode primitive with no texcoord array the constant generic texcoord
  (0,0,0,1), which samples a transparent texel and the line is thrown out by the
  alpha test - the walls up close had no top edge at all.  The port's wall
  passes supply that texcoord and colour through client arrays
  (`src/tron/gWall.cpp`).  On the far wall band the builds now measure the same:
  24.1 % against 23.8 % of pixels above luminance 40, mean green 37.9 against
  36.7, 9.4 % against 8.8 % above 120.
- Playback used to skip rendering whenever the port's clock ran ahead of the
  recording (`src/render/rSysdep.cpp`), which left a cleared canvas under the
  HUD at exactly the gates the captures were taken at.  Playback frames now
  render one step and present like live ones.
- The distance grid is at parity at matched poses.  Window peak brightness
  255 / 253 / 211 against the native's 255 / 255 / 255 in the far, mid and left
  windows, bright-row coverage within 1.5 points, and a row profile whose
  sampling period, mean and standard deviation match.  An earlier revision of
  this section reported the opposite; that was an artefact of counting dark rows
  as lines, which is why the metrics are now peak, coverage and row profile.
- The positional-light correction had silently stopped being applied: its patch
  anchor no longer matched the generated emulation, so `build.sh` ran the script
  and the script changed nothing.  The anchor is rebuilt from the emitted source
  and the build now reports `applied positional vs directional light
  distinction`.  There is no matched before-picture at the same gate, so this is
  not counted as a measured visual fix, only as a patch that now does what it
  claims.

What is still open, with today's numbers from a frame-matched pair at game time
2.46 (camera 107.83, 69.69 on the port against 107.83, 69.60 native):

- The floor and the trail nearest the camera.  In the band from 0.61 to 0.86 of
  frame height the native has 8.9 % of its pixels above luminance 120, the port
  6.9 %; over the pixels where the native is bright, the port reads RGB
  (31,33,32) with a median of 0, so about half of them are simply black.  The
  candidate mechanisms have been measured one by one and rejected: the floor
  texture is the same file, size, wrap and filter on both sides (the native
  uploads 1x256 and 256x1 copies as well), the wall passes are all issued in the
  port's command stream, the line vertices are submitted and inside the clip
  volume against the port's own projection matrix, the projection matrix agrees
  with the native's to two decimals, and a depth-test tie is not the cause - the
  engine already compares with `GL_LEQUAL`, so the small lift the line carries
  does not have to beat a depth step.  Still open is the `glPolygonOffset(-2,-5)`
  both builds use around floor-adjacent geometry (`rScreen.cpp:1228`): those
  numbers are depth-buffer steps, so on the WebGL context's 16-bit depth buffer
  the same call moves a fragment about 256 times as far in depth as on the
  reference's 24-bit one (7.6e-5 against 3.0e-7 at these view distances).  That
  is an over-lift, which would carry near geometry through the floor's own
  layers rather than hold it back.  A page-side hook meant to neutralize the
  offset never produced a frame, so this stays arithmetic rather than measurement.
- A page-side probe once reported `GL_INVALID_ENUM` on quad-family
  immediate-mode draws.  The client-array draws described above report no GL
  error (checked with `glGetError` around every `glDrawArrays` in the helper),
  so the report is not reproduced by the code path that draws the walls and
  stays open as an observation about the immediate-mode paths.
- The spectator camera desyncs a few seconds into a replay: the recording stores
  no camera state, so the two builds follow different cycles later on and only
  the first gates can be paired.
- The cycle body itself measures at parity.  Over the lower half of the frame the
  whitish specular core covers 6944 px on the native and 6989 on the port, mean
  215,215,215 against 213,213,213, and the saturated green body colour is
  identical (mean 0,253,0 against 0,254,0).  Saturated-green *coverage* is not at
  parity there (8120 against 2356 px), but that is the near-field geometry
  described above: measured as luminance coverage over the far wall band the same
  pair is at parity (24.1 % against 23.8 % above luminance 40).

An earlier commit here claimed the projective texture-coordinate fix explained
the fading grid.  Paired measurement disproved that; it stays as a conformance
fix and is not counted as a visual fix.

### Reproducing the comparison

The recording used for this is `webgl/harness/perp2.aarec`: a single-player
round on the default map, 60 fps capped, with the camera driven around the
perimeter of the stage, so walls, floor and cycles all appear edge-on and
head-on.  The native build is configured with the same `autoexec.cfg`
(`webgl/harness/autoexec.cfg`) and played back under Xvfb:

    src/armagetronad_main --norun --loglevel 4 \

`--playback FILE` takes the file as a separate argument, not joined by `=`.
Keystrokes are sent with `xdotool`; the menu sequence that starts a single
player round is `w:4500 e:1500 d:700 e:1500 e:1500` (wait, then Enter).  A
comparison build prints one line every eleventh rendered frame:

    FRAME <n> state 6 gt <game time> ncam <c> pos <x> <y> h <h> dir <dx> <dy>

The port writes the same line to `stdout` (the browser console); the native
writes it to `stderr`.  `webgl/harness/cdpd.py` drives the port over the Chrome
DevTools protocol: it watches that stream, fires a screenshot when the step
condition is met (`N:341,s` grabs at frame 341) and writes `<tag>-NN.png` plus a
`<tag>-shots.txt` manifest line carrying the pose.  `webgl/harness/glinstrument.c`
is an `LD_PRELOAD` interposition for the native build that counts draw calls per
primitive mode and prints the projection matrix, which is how the two builds'
command streams were compared.  The analysis tools take those manifest lines on
stdin (`png rect tag gt pos dir`): `gridprofile.py` profiles the grid lines per
band, `parity_report.py` reports window peak, coverage and row profile, and
`modelshape.py` extracts the light-cycle silhouette.

### Comparison instrumentation

Captures are paired by a stamp that a comparison working tree adds to
`gGame::Render`; it is deliberately not committed because it prints every
eleventh rendered frame and would flood a player's console.  The line format is
the one quoted above: both builds print it, the port to `stdout` (the browser
console) and the native to `stderr`, and the capture driver keys its gates off
the ` FRAME ` field rather than any particular prefix.

The taps used while tracking the divergences are working-tree only for the same
reason: an event tap in `EventArchiver::Archive`, which is what exposed the
SDL 1.2 against SDL 2 keysym mismatch in replayed input; a texture-upload tap in
`rTexture.cpp`; a wall-pass tap in `gWall.cpp`; spark taps in `gSparks.cpp` and
`gCycle.cpp`; and a GL-error tap around every `glDrawArrays` in the
client-array helper.  Page-side hooks - `getContext` wrappers logging GL state
or a draw census - are written into `webgl/dist/` by hand and referenced from
the generated `index.html`; `webgl/build.sh` wipes `dist/` on every run, so they
are applied after the build and never committed.

## Multiplayer

Browsers cannot send UDP, and Armagetron's protocol is UDP, so network play
needs the bridge in `webgl/proxy/`:

```sh
cd webgl/proxy && npm install
PROXY_PORT=8091 node proxy.js                       # ws://
TLS_CERT=... TLS_KEY=... PROXY_PORT=8443 node proxy.js   # wss://
```

Then open the game page with `?proxy=ws://host:8091/` (or
`?proxy=wss://host:8443/`). The https deployment requires `wss://`, otherwise
the browser blocks the connection as mixed content. The bridge maps each
WebSocket session to the UDP socket of one server; the target can be an
address or a host name (`?target=host:port`), names are resolved by the
bridge, not by the client. This path is not covered by CI — it was verified
against a native dedicated server of the same version running next to the
dev site.

Join from the menu: Play Game → Multiplayer → Custom Connect (or a Server
Bookmark) and give the address and the port of the server. The login
handshake and the two sync rounds of a join are stepped one iteration per
animation frame (`sn_ConnectPump`, `sn_SyncStart`/`sn_SyncStep`) because the
browser only delivers the server answer while the frame function is off the
JS stack.

### Server browser

Both browse modes work through the bridge; the blocking native browse loops
are stepped per animation frame instead (`nServerInfo::PumpBrowse()`, called
from the browser menu's redraw).

- *Online Multiplayer* talks to the master servers in the master list: the
  list is `config/master.srv` from the data bundle plus every
  `ADD_MASTER_SERVER <name> <port>` (config file or console). Master names
  are resolved by the bridge. The connect, the list request and the answer
  collection all run on the frame clock; a master that does not answer is
  retried, then the list is sorted and shown.
- *LAN Multiplayer* sends a `RequestSmallServerInfo` broadcast to ports
  4534-4540, one port per 0.25 s. The bridge turns each sweep session into a
  real UDP broadcast and prefixes every answer with the answering
  server's address, which is what lets the client query and join the servers
  it just discovered. Hosts a broadcast cannot reach (separate machine,
  loopback) are added with `LAN_EXTRA=host[:port][,host[:port]]` on the
  bridge: every sweep datagram is replayed to them as a unicast.

## Limitations

- No background music: the SDL1 JS port has no mixer, so only sound effects
  play.
- The toolchain is pinned (`webgl/SDK_VERSION`) because the build depends on
  `-s LEGACY_GL_EMULATION=1`, which newer emscripten releases are phasing out.
- Single-threaded: no pthreads/SharedArrayBuffer, so no COOP/COEP requirement.
- Network play needs the bridge, as above.
- LAN server browse stays empty: it probes the local network with a broadcast,
  and the bridge maps one WebSocket to one server address.
- Frame rate is bounded by the fixed function emulation (every immediate mode
  call is re-tessellated in JS) and by the browser's software renderer when no
  GPU is available. Measured in headless Chrome with SwiftShader: menus run at
  ~60 frames/s, a round at ~1.6 frames/s. The HUD `FPS:` readout and the game
  clock both follow that rate correctly, so a low number is the renderer, not a
  broken timer.
- The top level main menu cannot be left. The native build exits the process
  there; a page has no process to exit into, so leaving that menu re-opens it
  and its "Exit game" item is not shown.

## Deployment

GitHub Pages must build from Actions (repository **Settings → Pages → Build and
deployment → Source: GitHub Actions**). Then a push to `webgl` runs
`WebGL build & Pages`: it builds the toolchain, bootstraps autotools, builds
the wasm, uploads `webgl/dist/` as a Pages artifact and publishes it at
<https://smarioman.github.io/armagetronad/>. Pull requests to this branch build
and keep the site build checkable but do not deploy.
